## Legacy preservation and merge

1. Identify the running `metamuseum_container` image ID, its deployed source SHA and its Compose/environment configuration on the production host. Do not put secrets in Git.
2. Create preservation branch `legacy-flask` and annotated tag `production-pre-v2-20261031` at the verified production SHA. If it differs from `974bbfd`, preserve both the actual production SHA and the legacy `master` baseline. The branch is a recovery reference, not a commitment to new Flask development.
3. Preserve the running image with a separate immutable tag and ID, and archive it if needed. Do not rely solely on a continually overwritten `latest` or `rollback` tag.
4. Collect release-preparation commits on the working branch and review them in a PR targeting `master`. Prefer a normal merge commit (`--no-ff`) to record the generation change rather than squashing all 82 commits.
5. After merging, `master` is the canonical code branch. Keep the feature and preservation branches until the first deployment and rollback checks are complete.

Branches and tags recover code. They do not replace the production image, secret configuration or MongoDB/media backups.

## Version policy

Replacing a framework alone does not require a SemVer major version. [SemVer](https://semver.org/) is based on compatibility changes to the public API. This release replaces the entire UI, server and deployment unit, changes the session cookie and retires some Flask-Admin internal protocols, so `2.0.0` appropriately identifies the new product generation.

- Preparation/staging candidate: `2.0.0-rc.1`. Use a new RC number and tag for a revised candidate.
- Final release: create tag `v2.0.0` and a GitHub Release at the validated source commit. If RC and final image version labels differ, build and identify a new final image.
- Once finalized, align the backend package, frontend package/lockfile, FastAPI version information and generated OpenAPI contract to the same product version. The running image's Git SHA/release version must also be identifiable.
- Existing `/api/v1` URLs, Mongo schema versions and avatar/wall protocol versions are separate from the product version. Do not rename all APIs to `api/v2` or change schema numbers solely because the product is `2.0.0`.
- Do not invent a historical `v1.0.0` release that was never published. Record the Flask baseline with an explicit legacy/production preservation tag.

## 2.0 release scope

| Surface | Included behavior and limits |
| --- | --- |
| Gallery / permanent URLs | Existing room/wall/artwork IDs and URLs, images/GLTF/splats, image-only 2D display, layout/cutout/boundaries/spawn presets. |
| TV wall display | Standalone `/wall` view fitted to the window, `refresh`/ETag and realtime wall state. Receives updates without creating a visitor/avatar and has no input or administrator playback-command authority. |
| Interactive walls | 44 source presets, hierarchy/text/shapes/motion/history/JSON, Mongo presets and independent applied snapshots, uploads and conflict checks. Same-room pointers and playback clocks are shared. |
| Human avatars | Four original humanoid presets and legacy choices, color/face/accessories, client motion/IK, relayed final joints and detail management. Untracked legs are estimated. Finger articulation and arbitrary model uploads are excluded. |
| Web input | Desktop movement/look, mobile floating nipplejs joystick, tab-local visitors and reconnect. |
| Administration / compatibility | Eleven resources, existing account hashes and media paths, CSRF/permission/reference checks. Users must sign in again once for the session change. |
| Media / services | MP4, FFmpeg RTSP/HLS, separate DOM webpage/YouTube players, WebRTC voice, AR/gesture and configured AI/STT adapters. External-service availability and production-network conditions are not guaranteed. |

The legacy Flask runtime and Flask-Admin built-in export/file/ajax-lookup protocols are outside final support. Those internal administration routes return authenticated `410` responses and are replaced by the React administration UI. API JSON/CSRF login and the side-effect-free GET logout entry also differ from legacy form handling. Webpages/YouTube do not composite arbitrary iframes inside WebGL. Detailed differences are preserved in the [feature contract](../../contracts/feature-parity.md).

## Research features and validation scope

- Procedural gaze is a default-off research algorithm. Attention weights, filters and gaze angles are configurable; it does not establish actual eye tracking, attention measurement or that another person cannot notice it.
- GaussianAvatars subject 306 is a local research head/bust model. FLAME/subject data is excluded from the repository and production image and blocked by the production asset API and catalog. Dynamic Gaussian LOD, large-population performance and full-body support must not be advertised as release features. See [development status](../gaussian-avatar-gaze.md).
- Limited LG V35 checks covered WebGL, appearance save/reload, actual touch movement and updates seen by a desktop observer. No comprehensive phone CPU/GPU/RAM/FPS, thermal or battery measurements were performed.
- Actual Quest 3 VR/controller/hand acceptance was not completed. Keep this separate from A-Frame mock XR validation. A promise of XR support requires a brief actual-device entry/controller/hand/exit check on the deployment candidate.
- Voice CI uses actual WebRTC connections and a synthetic microphone. Physical microphones/cameras, different external networks and TURN require separate operational checks.
- YouTube CI distinguishes successful playback/pause/seek from error/original-link checks for explicit `LOGIN_REQUIRED` bot blocking. Recorded `external_blocked` results are not successful playback. Local actual YouTube playback and controlled-player checks using the application HTTP/Socket.IO path are separate evidence.

## Recommended cutover sequence

1. Identify current production source/image/configuration and preserve the branch/tag/image.
2. Briefly rehearse staging restoration and legacy-image rollback from paired production backups.
3. Fix preflight checks, permissions and rollback conditions in the deployment proposal; finalize README/CHANGELOG/version labels. Record the validated RC image and its identity.
4. Merge normally into `master` through a PR and check CI for the merge result. Do not run the first public cutover automatically.
5. Complete image building before pausing writes. At cutover, stop HTTP and Socket.IO writes together using the agreed method, such as stopping the legacy container; take a final consistent DB/media snapshot and switch to the identified versioned image. Do not assume the app has a dedicated read-only mode. Plan a short service interruption for the first cutover.
6. Immediately after cutover, keep external writes paused and allow only operators to check health/login, representative room/wall/image/splat/GLTF, two-tab realtime behavior, preset upload/apply and shared MP4. Prepare operator-only access before cutover. Include a separate actual-device check for any promised XR scope. Reopen external access/writes after smoke checks pass; on failure, keep restrictions in place while deciding rollback.
7. Record successful source, image digest, backups and production-check results in the release. Decide separately whether to enable automatic master deployment after initial stabilization.

If only the application fails, return to the preserved image and legacy configuration. For data incompatibility or corruption, stop writes and restore the paired DB/media snapshot. State the recovery point because data written after that snapshot may be lost. Reverting a Git branch alone is not data rollback.
