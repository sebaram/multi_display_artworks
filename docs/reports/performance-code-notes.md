# Performance methodology and runtime cost notes

Read-only source review on 2026-10-29, branch `codex/fastapi-react-interactive-walls`, source baseline `d80bd32845d8716f77f2aa7afdb7d3db626d73de`. These are code-backed explanations and measurement controls, not device benchmark results. No product code was changed for this review.

## Scope and device labels

Actual desktop measurements on the stated workstation can establish its performance at the tested browser, drawing-buffer size, content, camera path, and refresh cap. A 390 × 844 CSS-pixel viewport, DPR 2, and a 4× CPU slowdown on that workstation is a **desktop mobile-layout stress profile**. It is not a measured phone. The GPU, worker CPUs, memory bandwidth, video decoder, thermal behavior, and WebXR runtime remain those of the workstation. Chrome explicitly describes device mode as an approximation; its CPU throttle suspends the main thread and does not throttle the GPU process. [Chrome device-mode limitations](https://developer.chrome.com/docs/devtools/device-mode#limitations), [Chrome throttling implementation and limits](https://developer.chrome.com/blog/devtools-grounded-real-world#how_cpu_throttling_works_in_devtools).

Quest 3 remains **unmeasured** until the same fixtures run in its actual browser and immersive session. Budget markers of 13.89 ms / 11.11 ms / 8.33 ms correspond mathematically to 72 / 90 / 120 frames per second; they are comparison targets, not predictions or a claim about the active device mode.

## What grows with scene content

| Runtime path | Cost that grows | Source evidence and practical consequence |
| --- | --- | --- |
| Room construction | All walls and elements, not just the current view | `frontend/src/scene/mountRoom.ts:313–392` creates the whole hierarchy and requests each image/model/splat. There is no application-level distance streaming, room-cell loading, LOD selection, batching, or repeated-model instancing in this loop. Ordinary meshes can still benefit from the renderer's frustum checks. A bigger room with unchanged counts primarily changes view/distance/coverage; it is not automatically more expensive. |
| A-Frame cursor raycaster | Candidate object count; mesh geometry when a bounding volume is hit | `mountRoom.ts:101–107` includes every `.artwork` and `.wall-surface`. The pinned `frontend/public/vendor/aframe-1.6.0.min.js:1`, raycaster component, defaults `interval` to 0 and calls recursive `intersectObjects`. High object counts can therefore add CPU cost even when draw-call counts are low. A model test must preserve cursor/raycaster behavior if it is intended to represent the room. |
| Additional live-wall pointer pass | Live design wall count on pointer movement | `mountRoom.ts:423–486` creates a ray and loops over wall meshes. The 50 ms gate limits accepted interaction attempts after a hit; keep the same pointer location/path between runs. A stationary off-canvas pointer and an actively moving pointer are different workloads. |
| Compact minimap | All wall/element/preset markers each window animation frame | `frontend/src/scene/legacy/minimap.js:58–129` visits walls/elements/presets and paints labels; `:231–243` redraws the compact map every frame and a second map while its dialog is open. Main scene frustum visibility does not reduce this work. `frontend/src/scene/realtime.ts:204–217` mounts it only when controls and a boundary are enabled. Keep this enabled consistently and keep the expanded dialog closed in the main comparison. |
| Live wall design | Every bound wall, including walls behind the camera | `mountRoom.ts:616–631` calls every wall renderer on each window RAF and marks every resulting main-scene texture dirty. A paused design still passes through rendering/compositing; there is no visible-wall or unchanged-frame early exit here. This cost is separate from main scene draw calls. |
| Gaussian splats | Every instance's data, worker, sort scan, uploads, and projected splat coverage | Each component owns a worker (`frontend/public/vendor/gaussian-splatting.js:240–254`), two data textures and an index attribute (`:55–84`), and a non-frustum-culled mesh (`:215–216`). The worker scans all loaded vertices before behind-camera/tiny/cutout rejection (`:525–573`), then uses a fixed 65,536-bin counting sort (`:575–585`). `:456–471` requests another sort whenever the previous one is ready; it does not check whether the camera changed. More instances can raise worker CPU while the main thread still appears lightly loaded. |
| Remote visitors | Visitor count and incoming pose/hand changes | `frontend/src/scene/legacy/rendering/render-loop.js:25–37` interpolates every buffered user every A-Frame tick. `frontend/src/scene/legacy/rendering/scene.js:116–159` maintains avatars and transforms; hand-state changes can rebuild hand entities (`:58–80`). Pose history is bounded to 8 samples per user (`frontend/src/scene/legacy/core/sync-constants.js:7`), not unlimited frame history. A one-visitor scene benchmark is not a multiplayer capacity test. |

The ordinary Three.js draw count depends on what is submitted in the current view; the object/texture/resource count and worker cost need not drop when the camera turns away. This code also has no application occlusion system that unloads content behind walls. Keep total content and visible content as separate fields in the report.

## Textures, models, and sharing

- Image and primitive geometry reuse can be cheaper than unique assets. The pinned A-Frame material system has a `sourceCache` keyed by source identity, and its geometry component defaults `skipCache` to false (`frontend/public/vendor/aframe-1.6.0.min.js:1`, material system and geometry component). The room itself creates separate entities/materials and does not batch them (`mountRoom.ts:332–358`). Shared source data is not proof of a shared draw call. Report observed GPU texture/geometry counts instead of assuming one allocation per element or one allocation per file.
- Use separate reused-URL and unique-URL 1024 × 1024 image cases. Record the number of distinct source identities, decoded dimensions, and texture settings. Compressed file bytes are not GPU memory; mipmaps and upload formats also matter. Rotate through all walls in warmup so initially offscreen images have had an opportunity to upload before comparing steady resource counts.
- Each glTF entity has its own loader/model component; the pinned component loads a model into each entity (`frontend/public/vendor/aframe-1.6.0.min.js:1`, `gltf-model` component). HTTP request reuse is not mesh instancing or guaranteed parsed-resource sharing. A synthetic 10k-triangle static glTF fixture should have a controlled primitive/material count as well as triangle count. `mountRoom.ts:351–358` does not attach an animation mixer, so this fixture does not characterize animated/skinned models.
- Repeated splat URLs do not share the component's worker, parsed data, or GPU textures. The allocation width is the adapter's `MAX_TEXTURE_SIZE`, and height is rounded up for the vertex count (`gaussian-splatting.js:47–67`). The two RGBA32 data arrays alone are 32 bytes per padded texel on the CPU, with corresponding GPU texture storage; the index array adds 4 bytes per padded texel. The worker retains 16 floats per vertex (`:357`, `:451–454`, `:594–602`) and allocates sort scratch/output arrays (`:531–585`). These are code-level byte counts, not a complete driver-memory estimate. Main-isolate JS heap metrics cannot summarize them all.

## Live-wall resolution, contexts, and media

Each bound design uses a 1024-pixel-wide canvas, with height `max(128, round(1024 × wall.height / wall.width))` (`mountRoom.ts:208–214`). Its source scene creates an independent antialiased WebGL renderer with `preserveDrawingBuffer: true`, forces pixel ratio 1, and creates its own environment render target (`frontend/src/wall-engine/reference/scene.js:16–29`). `:193–196` sets the source drawing buffer to the wall canvas size. Physical wall distance and the main scene's mobile viewport do not lower this source resolution.

The compositor owns three Canvas2D surfaces at that same width/height: output, intermediate frame, and cached text (`frontend/src/wall-engine/compositor.js:13–14`, `:65`). Every live frame copies WebGL source → intermediate canvas, draws media/text, then copies intermediate → output (`:145–162`). The room then requests a canvas-texture upload to its separate main renderer (`mountRoom.ts:625–626`). There is also a small environment canvas per source renderer. Counting only the main scene's WebGL context misses these costs. A 1-versus-4 design case is representative; large design counts must also check context-loss events rather than assuming linear unlimited growth.

Legacy wall videos each create an HTMLVideoElement, preload and play it independent of camera visibility; HLS uses a separate Hls instance when necessary (`mountRoom.ts:171–199`, `:284–296`). Design video layers likewise each own a decoder element and can seek, play, and `drawImage` every compositor frame (`compositor.js:50–63`, `:129–143`). Identical URLs do not imply one video decoder. Use a local deterministic clip with known codec, resolution, frame rate, and number of active players; verify currentTime advances and report dropped/decoded video frames if exposed. A paused, failed, CORS-denied, blocked-autoplay, or placeholder video is a different workload. Design YouTube layers are textual placeholders in the composed wall and open a separate synchronized player (`compositor.js:153–158`, `:168`), so they do not measure embedded YouTube decoding.

`webpage` room elements fall through to a generic flat plane (`mountRoom.ts:384–391`). The actual sandboxed iframe is conditionally created only after opening the sidebar player (`frontend/src/features/room/Room.tsx:820–839`). Report these as separate cases: many webpage markers, and one explicitly opened deterministic webpage. A marker-only test cannot establish webpage rendering cost.

## Device settings that can silently change the workload

**Splat resolution override:** every splat component defaults to `pixelRatio: 1` and `xrPixelRatio: 0.5` and applies those values to the shared main-scene renderer when it starts (`gaussian-splatting.js:7–18`). A DPR-2 emulated profile containing splats can therefore draw at DPR 1. Capture `window.devicePixelRatio`, `renderer.getPixelRatio()`, CSS canvas bounds, and actual drawing-buffer width/height after all components load. Benchmark either the native behavior and disclose the override, or an explicitly labelled fixed-resolution control. Do not silently compare two different buffers under the same DPR label.

**Readiness:** `mountRoom.ts:584–610` invokes `onReady` before awaiting realtime setup. Direct media/model/splat loads are asynchronous. Before warmup, assert the expected element/wall counts, loaded image dimensions, each glTF model, each splat's `loadedVertexCount` and first sorted mesh, active video playback, and the intended realtime/minimap state. Collect asset/network/component errors. A scene `loaded` event plus an arbitrary delay is insufficient evidence that a large fixture finished loading.

**Refresh and visibility:** keep the benchmark tab foreground/visible, record visibility transitions and the actual display/browser refresh cap, and run one measured context at a time. A 60 Hz RAF plateau means only that the workload met that pacing cap; it does not establish unlimited GPU headroom. FPS should be count / actual elapsed duration, with p50/p95/p99 RAF intervals and explicit thresholds. Averages alone can hide long stalls. The RAF sampler is a pacing measurement, not proof that every callback produced a presented frame.

**Reject or separately label invalid phases:** software rendering such as SwiftShader cannot support a result attributed to the workstation GPU; a hidden/throttled tab cannot support a foreground FPS claim; lost contexts or failed/unloaded assets cannot support the intended full-content workload; and a monoscopic non-immersive canvas cannot support an XR/stereo result. Preserve the raw failure and validity flag instead of converting missing telemetry to zero or reporting it as a successful fast run.

## Metric interpretation

| Metric | Valid interpretation | Limitation to show |
| --- | --- | --- |
| Window RAF FPS and interval percentiles | Foreground desktop page pacing in the measured phase | Not headset refresh, video frame rate, or directly measured presentation FPS. |
| `ΔTaskDuration / elapsed` using default CDP time domain | Fraction of wall time spent inside main-thread tasks | Label as main-thread task occupancy, not CPU utilization; blocked/suspended time within a task can count. In particular, main-thread throttling changes wall-time task duration. |
| `ΔThreadTime / elapsed` when available | Main renderer-thread CPU time, normalized to one logical core | Excludes workers, GPU process, other browser threads. Preserve unavailable values rather than substituting zero. |
| `SystemInfo.getProcessInfo` CPU deltas | Cumulative CPU seconds across all threads of each identified browser process | Report per-process type and sum for the owned browser; one-core-equivalent percentages can exceed 100%. Machine-normalized CPU divides by logical processor count and must have a different label. |
| `JSHeapUsedSize` | Main inspected V8 isolate's reported used heap | Not total RAM; excludes worker heaps, GPU allocations, decoder buffers, and much external backing storage. |
| Owned Chrome process working sets / private commit | Browser process memory observed by Windows | Working sets are resident bytes and can include shared pages; summing them can double count shared pages. Private committed bytes are not resident RAM. Report separately and identify which PIDs are included. |
| `renderer.info.render.calls/triangles` and `.memory.geometries/textures` | Submission/resource counts for the main Three renderer | Counts, not bytes or whole-app rendering cost. Live-wall source renderers and Canvas2D are separate. Read draw statistics after render because the renderer resets them automatically. |
| Disjoint timer around main `renderer.render` | GPU time for commands enclosed in that context's query | Excludes independent live-wall WebGL renderers, Canvas2D composition, video decode, other GPU apps, and presentation. Poll asynchronously, discard disjoint samples, delete queries, and do not block with `finish`/readback. |
| NVIDIA adapter utilization, used memory, power, temperature | Whole-adapter telemetry over the sample interval | Includes the desktop and other applications; do not title it app-only GPU usage/VRAM. Record an idle baseline and actual sample count. WDDM may not expose useful per-process dedicated memory. |

CDP's protocol explicitly distinguishes default monotonic `timeTicks` from CPU-running `threadTicks`; Chromium exposes a separate `ThreadTime` metric and measures default `TaskDuration` in the selected time domain. [Official Performance protocol](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Performance.pdl), [Chromium metric implementation](https://raw.githubusercontent.com/chromium/chromium/main/third_party/blink/renderer/core/inspector/inspector_performance_agent.cc). `SystemInfo` defines `cpuTime` as cumulative seconds across all process threads. [Official SystemInfo protocol](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/SystemInfo.pdl). GPU query results must be available and non-disjoint before use. [Khronos timer-query specification](https://registry.khronos.org/webgl/extensions/EXT_disjoint_timer_query_webgl2/).

## Representative cases and repeatability

Use a deterministic fixture manifest: room dimensions and area, wall count/layout, element type/count, distinct source count, triangle/primitive/material counts, splat source/visible counts, texture dimensions, active video counts/specification, design preset/configuration and canvas sizes, and visitor count. Keep a fixed seed and identical camera trajectory/velocity/yaw duration. Reused-image and unique-image cases should differ in source identity, not scene layout. Fixed physical room size with rising content counts isolates content pressure; fixed content counts across room sizes isolates spatial/layout effects. Avoid claiming which variable caused a change when both changed together.

A compact primary matrix is: empty room; reused 1024 images at several counts; unique 1024 images at matching counts; controlled static 10k-triangle models at increasing counts; 100k-splat files at 1/4/8 instances; 1/4 live designs; 1/4 active videos; webpage markers plus one opened iframe; and one explicitly specified mixed scene. Use desktop 1440 × 900 DPR 1 and 2560 × 1440 DPR 1, plus the clearly labelled mobile-layout stress profile. Dynamic-wall/video fixtures should be independent of the static-element count matrix so their costs remain interpretable.

Wait for readiness, traverse a full yaw during warmup, then measure the same motion phase. Eight seconds of warmup plus twelve seconds measured twice can be a useful first sweep; preserve each run separately. Twelve 1 Hz GPU samples and two repeats are not enough to characterize thermal stability or rare stalls. Rerun the threshold/borderline cases longer, and show run-to-run spread rather than smoothing it away. Separate cold-load timing/peak memory from warmed steady-state performance. Use the production build, record browser version/launch flags, actual adapter/driver, and any CPU slowdown, network controls, missing metrics, asset failures, or context losses in machine-readable output.

## Immersive XR checks still required

The visible VR button calls A-Frame `scene.enterVR()` (`Room.tsx:387–393`), and the remote-pose loop intentionally uses A-Frame tick for both desktop and XR (`legacy/rendering/render-loop.js:15–18`, `:40–46`). Actual headset instrumentation should attach to the renderer/XR session animation loop, confirm `renderer.xr.isPresenting`, record view count and view/framebuffer dimensions, session visibility, active pacing, and relevant reprojection/dropped-frame statistics if the device exposes them. A one-camera desktop canvas has neither headset stereo submission nor the headset compositor's cost.

Live-wall animation currently uses **window** RAF (`mountRoom.ts:616–631`). W3C notes that these callbacks can stop on standalone immersive devices when the page has no rendering opportunity, and can run at different timing from XR callbacks. Therefore live walls might freeze or update at a different cadence in immersive Quest use; this is a code-backed compatibility risk requiring a real-device check, not a verified Quest defect. [W3C WebXR animation frames](https://www.w3.org/TR/webxr/#animation-frames).

The hand-tracking control separately requests its own immersive session (`frontend/src/scene/legacy/interaction/hand-tracking.js:139–168`); that path should not be treated as proof that it is integrated with the main A-Frame rendering session. Record which entry path and input features are actually active during any later headset run.

## Cleanup evidence and remaining limits

Room disposal stops the wall RAF, pauses/releases media, ends an active XR session, disposes/loses the main renderer context, and removes the scene (`mountRoom.ts:632–644`). Wall lifetimes dispose each design renderer (`:253`, `:166–167`); the source renderer disposes geometries/materials/environment and loses its context (`wall-engine/reference/scene.js:52–56`, `:215`), and the compositor releases video sources, URLs, fonts and hidden DOM (`wall-engine/compositor.js:35–38`, `:169`). The splat lifecycle patch aborts downloads, terminates its worker, revokes its Blob URL, and disposes geometry/material/two textures (`gaussian-splatting.js:25–40`).

This is evidence of intended cleanup, not a measured absence of leaks. A separate repeat-mount/update/dispose test should inspect worker/context/DOM/media counts and memory returning toward a warmed baseline. The vendor glTF component's `remove` only detaches its mesh (`aframe-1.6.0.min.js:1`); repeated model URL replacement within a live room deserves explicit resource-count testing. A single fresh-page steady-state snapshot cannot establish lifecycle behavior, and no actual phone or Quest 3 behavior was verified in this review.
