04
INTERPRETATION

측정으로 말할 수 있는 것

실제 휴대폰·Quest 3의 수용량은 아직 정하지 않았습니다. 아래 권고는 PC 측정과 소스 검토에 근거한 초기 설정 방향입니다. 기기별 최대 이미지 수·동적 벽 수·예상 FPS를 보장하지 않습니다.

초기 콘텐츠 구성 권고

  • 반복 이미지는 소스 URL을 재사용하고, 고유 이미지의 텍스처 해상도·동시 업로드를 관리합니다. 파일 크기와 GPU 메모리는 다른 값입니다.
  • 동적 디자인 벽·영상은 활성 수와 해상도를 먼저 줄여 검증합니다. 디자인 소스는 벽마다 별도의 1024 × 576 WebGL·Canvas2D 경로를 가집니다.
  • 방의 물리적 크기보다 실제 콘텐츠 수·고유 자산·화면 점유·활성 렌더러를 함께 관리합니다. 공간이 커졌다는 이유만으로 같은 비율의 비용 증가를 가정하지 않습니다.

기기 검증이 필요한 코드 경로

  • 가우시안 스플랫은 메인 렌더러 DPR을 1, XR 프레임버퍼 스케일을 0.5로 덮어씁니다. 선명도를 바꾸는 설정이며, 모바일 DPR 2 조건도 실제 버퍼 크기를 확인해야 합니다.
  • 디자인 벽은 window RAF에서 갱신됩니다. immersive XR에서는 이 콜백이 멈추거나 XR 루프와 다른 간격으로 실행될 수 있습니다. 실제 Quest 고장으로 확인된 사실은 아닙니다.
  • 거리별 스트리밍·LOD·반복 모델 인스턴싱은 없습니다. 미니맵·레이캐스터·스플랫 정렬은 전체 콘텐츠에 대한 CPU 비용을 만들 수 있습니다.

다음 실제 기기 검증

휴대폰은 정확한 모델·브라우저·전원·발열 상태를 기록하고 같은 장면을 실행해야 합니다. Quest 3는 실제 immersive 세션에서 XR 표시 여부·뷰 수·눈별 버퍼·활성 주사율·재투영·컨트롤러/손 입력·동적 벽 갱신을 확인해야 합니다. 기준 근처의 케이스는 긴 실행과 반복 진입·이탈로 다시 검증합니다.

프레임 시간 예산의 산술: 72 Hz = 13.89 ms, 90 Hz = 11.11 ms, 120 Hz = 8.33 ms. 이는 비교용 예산이며 Quest 3에서 이 보고서의 장면이 달성한 결과나 예상 FPS가 아닙니다. Meta WebXR 성능 워크플로

METHOD

측정 순서와 통제 조건

한 케이스의 실행

자산 준비 완료를 확인한 뒤 카메라를 수평으로 360° 회전합니다. 측정 중에는 스크린샷을 찍지 않습니다. 장면은 한 번에 하나씩 실행하며 전경·visibility·컨텍스트 손실·자산 오류를 기록합니다.

부하를 구분하는 방법

공유/고유 1024 이미지, 정적 GLB(인스턴스당 10,224 삼각형), 100k 포인트 스플랫, 디자인 벽, 실제 재생 영상, 웹페이지 표식, 혼합 장면을 별도 조건으로 둡니다.

웹페이지 케이스는 3D 평면 표식입니다. iframe은 요청할 때만 열리므로, 표식 20개를 동시 실행 웹페이지 20개로 해석하면 안 됩니다. 160 × 90 영상은 기능 확인용이고 1080p·4K 영상은 별도 부하입니다.

워크로드 명세와 반복 집계 규칙

종류방 한 변시험한 수해석

혼합 장면: 이미지 70% · GLTF 20% · 스플랫 2% · 웹페이지 표식 8%. 정확한 개수·고유 자산 수·고유 자산 파일 크기 합·포인트·삼각형·캔버스 크기는 케이스 상세와 JSON에 보존됩니다. 다중 사용자 동시 접속 수용량 시험은 별도입니다.
